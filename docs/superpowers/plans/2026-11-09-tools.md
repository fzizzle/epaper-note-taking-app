# Tools Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The rest of the writing tools: stroke eraser, lasso select (move, resize, copy, delete), snip, paste within the document, undo and redo, the page menu with rotation, and the pen's two side buttons (button 1 lasso, button 2 eraser, only while held).

**Architecture:** Every edit becomes a **change** (add items, remove items, replace items, rotate pages). A change has an exact inverse, which is how undo and redo work: undo records the inverse as a new change. The crash journal stores changes, one per line, instead of only strokes. The open PDF on the worker thread stays the one model of the document: the screen asks the session "what does this eraser trail touch?" or "what's inside this loop?", and the worker answers from the PDF. Each item (stroke or pasted snip) gets an app id, kept in the annotation's standard `/NM` name, so a change can name it across saves and crash replays. The geometry (hit tests, lasso, resize, paste placement) and the tool rules (which tool a stroke means, when fast-ink must be off) are plain Kotlin, tested on the laptop. The Android parts stay thin and are checked by hand. The plan ends with an owner tool session on the tablet: a **hard stop**.

**Tech Stack:** As in plan 2 (Kotlin 2.0.21, AGP 8.7.3, Gradle 8.11.1, compile/target SDK 35, min SDK 29, MuPDF `fitz:1.28.5`, Onyx `onyxsdk-pen:1.5.9`, JUnit 4.13.2, androidx.test). Nothing new.

**Spec:** `docs/superpowers/specs/2026-11-07-epaper-pdf-notes-design.md`, sections §6.2 (strip, page menu), §6.3 (all tools), §6.4 (rotation), §7.1 (snips as image annotations), §7.3 (journal). Pen facts: `docs/superpowers/probe-results.md`. What plan 2 learned on the tablet: `docs/superpowers/writing-screen-results.md`.

**Where this plan sits:** plan 3 of 5. Plan 4 adds the library, plan 5 conflict copies and crash replay onto a changed file.

Paths below are under `notes/app/src/`. `main/…` means `main/java/com/fzizzle/epapernotes/…`, `test/…` and `androidTest/…` likewise.

## Decisions for the owner (approve before Task 1)

These are the choices the spec leaves open that change how something behaves or how the code is built. Each is the builder's recommendation.

1. **Changes, not just strokes** (architecture). The journal and the session keep a list of changes. Undo and redo cover the current session only, as the spec says, and are lost when the app closes. At most 200 steps are kept.
2. **App ids in `/NM`** (architecture). `/NM` is the standard PDF "annotation name". Other viewers ignore it. Strokes from plan 2 have none; they're found by their PDF object number instead, and get an id when they're next moved.
3. **Resizing scales the line width too**, so a resized note looks like a zoomed copy, not thinner or bolder writing. The stroke data gets a width factor (`pn2`, and `pn1` still reads).
4. **Pasted snips are stamp annotations** with the picture drawn the right way up on the page they're pasted onto. If that page is rotated later, the snip turns with it, like ink.
5. **The eraser removes strokes when the pen lifts**, not one by one as it moves. While erasing, a thin grey trail shows where the pen went. Live removal would mean pausing fast-ink and redrawing the page for every stroke touched, which is slow and flashes on e-ink.
6. **Lasso and selection work with fast-ink paused.** The loop is drawn by fast-ink (thin grey). Once something is selected, fast-ink pauses: drag inside the box to move, drag a corner to resize, tap Copy or Delete in the small bar above the box, or tap outside the box to let go. While dragging or resizing, the box and a thin grey preview of the ink follow the pen; the real ink moves when the pen lifts.
7. **A stroke is selected when more than half its points are inside the loop**; a snip when its centre is. Loose loops still catch what they mean to.
8. **Snip** pauses fast-ink and shows the rectangle as it's dragged. After a snip, the tool goes back to the one before, and **Paste** appears. Tap Paste, then tap the page: the content lands centred on the tap, at the same size, and is selected, so it can be moved or resized straight away. Paste stays in the strip, so the same thing can be pasted again. The clipboard holds one item and lasts for the session.
9. **Snips are pictures at 2 pixels per point** (144 dpi), at most 2000 pixels on the long side, stored as PNG. Sharp enough for slide text, about 0.2–0.5 MB each.
10. **Undo or redo of a change on another page goes to that page**, so the owner sees what changed.
11. **Rotation turns pages clockwise** in 90° steps. "Rotate all" turns every page by 90° from where it is (pages already turned keep their difference).

## Global Constraints

- "Writing is never lost" (spec §2.6, §4). Every change must be in the journal before the PDF is changed, and the journal is cleared only "once the PDF save is confirmed" (spec §7.3).
- "Saving never blocks or stutters the pen" (spec §7.2). Nothing may pause fast-ink while the pen is down (plan 2 results, problem 1).
- Strip, left to right: `← library · pen · highlighter · eraser · lasso select · snip · undo · redo · ⋯ page menu`, then `‹ n / N ›` on the right. "After a copy or a snip, a **Paste** button appears in the top strip, and only then." The page menu holds "rotate this page" and "rotate all pages" (spec §6.2, §6.3).
- "Stroke eraser. Touching any part of a stroke removes the whole stroke. This applies to pen strokes, highlighter strokes, and pasted snips." (spec §6.3)
- Lasso: "Printed PDF content is never selected." Selection can be "dragged", "resized with corner handles (proportional scaling)", "copied, then pasted elsewhere in the same document", "deleted" (spec §6.3).
- Snip: "Drag a rectangle to capture that region as a picture, including the printed PDF content and any ink on it." Once pasted "it can be moved, resized, deleted, and lasso-selected, but not edited stroke by stroke" (spec §6.3).
- Buttons: "Button 1 switches to lasso select and button 2 to the stroke eraser. Each is active only while held, and releasing returns to whatever tool was active before." "A button counts only if it's held when the pen touches down." (spec §6.3). Button 2 arrives as the eraser end (`tool=ERASER`, Onyx's erase callbacks). Button 1 arrives as `STYLUS_PRIMARY`, often on hover 100–500 ms before touch-down. Keep `enableSideBtnErase(false)` (probe results §1, §2).
- "Undo and redo cover everything in the current session: strokes, erases, moves, resizes, pastes, deletes, rotations." (spec §6.3)
- Rotation "is saved into the PDF (the page's rotation property)" and "Ink already on a page turns with the page" (spec §6.4).
- "Annotations the app didn't create … must be kept intact on save" (spec §7.1). The eraser and lasso never touch them.
- Lightweight UI: no libraries, image files, fonts or animation. New strip buttons are drawn with plain shapes, like `StripButton` (owner, 2026-11-09).
- Only MuPDF code lives in `pdf/`. Only Onyx code lives in `ui/PenInput.kt`. Readable code: small files, plain names, comments that explain *why* (spec §5).
- Toolchain: `source ~/.local/opt/android-env.sh` first. JVM tests: `./gradlew :app:testDebugUnitTest`. Tablet tests: `./gradlew :app:connectedDebugAndroidTest` (uninstalls the app afterwards; restore All files access with `adb shell appops set --uid com.fzizzle.epapernotes MANAGE_EXTERNAL_STORAGE allow`). Hand checks: `./gradlew :app:installDebug`. All Gradle commands run in `notes/`.

## Review Focus

1. **A stroke is written while the worker is working out an eraser hit.** Both must be journaled and saved, and the save bookkeeping must stay right (Task 5: `strokeDuringEraseIsSavedWithIt`).

### Task 4: Geometry for the tools

**Files:**
- Create: `main/tools/Eraser.kt`, `main/tools/Lasso.kt`, `main/tools/SelectionBox.kt`, `main/tools/Clipboard.kt`
- Test: `test/tools/EraserTest.kt`, `test/tools/LassoTest.kt`, `test/tools/SelectionBoxTest.kt`, `test/tools/ClipboardTest.kt`

**Interfaces:**
- Consumes: `Item`, `Item.transformed` (Task 1), `Affine`, `Pt`.
- Produces (all in PDF space unless named otherwise):
  - `object Eraser { const val RADIUS_PT = 3f; fun hits(items: List<Item>, trail: List<Pt>): List<Item> }`. Ink is hit when any trail point is within `RADIUS_PT + half its width at that segment` of any of its segments (a one-point stroke is a segment of length 0). A trail of one point is a tap. An image is hit when a trail point is inside its box.
  - `object Lasso { fun selects(items: List<Item>, loop: List<Pt>): List<Item> }`. Even-odd point-in-polygon, the loop closed automatically. Ink: more than half its points inside. Image: its box centre inside. Fewer than 3 loop points select nothing.
  - `class SelectionBox(val bounds: Box)` in **screen pixels**, with `enum class Grip { NONE, MOVE, TOP_LEFT, TOP_RIGHT, BOTTOM_LEFT, BOTTOM_RIGHT }`, `fun gripAt(x: Float, y: Float, handlePx: Float): Grip` (corners win over `MOVE`, inside the box is `MOVE`, outside is `NONE`), and `fun drag(grip: Grip, dx: Float, dy: Float): Affine`: `MOVE` translates; a corner scales uniformly about the opposite corner, by the larger of the two axis ratios, never below `MIN_SIDE_PX = 24f` on the shorter side.
  - `class Clipboard(val items: List<Item>, val sourceToDisplay: Affine)`, made from a selection or a snip, and `fun Clipboard.placedOn(displayToPdf: Affine, at: Pt): List<Item>`. It maps the items through the source page into display points, centres them on `at` (display points of the target page), and maps them into the target page's PDF space. Every pasted item gets a fresh id. Images get their `quarterTurns` adjusted by the difference between the two pages' rotations, so they stay upright.
  - The uniform scale factor of an `Affine` (needed by `transformed`) is `sqrt(|a·d − b·c|)`. Add it as `Affine.uniformScale(): Float` in `main/geometry/Affine.kt`.

### Task 5: The session records changes, and undoes them

**Files:**
- Modify: `main/doc/DocumentSession.kt`, `main/doc/SessionEvent.kt`
- Test: `test/doc/DocumentSessionTest.kt`, `androidTest/doc/DocumentSessionDeviceTest.kt`

**Interfaces:**
- Consumes: `Change`, `ChangeJournal` (Task 2), `PdfPages.items`, `PdfPages.apply`, `PdfPages.rotation` (Task 3), `Eraser.hits`, `Lasso.selects` (Task 4).
- Produces:
  - `fun addStroke(page: Int, stroke: Stroke)`: as before, from the pen thread, now recording `AddItems(page, listOf(InkItem(ItemIds.next(), stroke)))`.
  - `fun record(change: Change)`: any thread. Journals, then queues the change for the PDF, then pushes it on the undo stack and clears redo. An empty change (no items, or no rotation difference) does nothing.
  - `fun erase(page: Int, trail: List<Pt>)`: on the worker, `Eraser.hits(items(page), trail)`; if any, `record(RemoveItems(page, hits))`.
  - `fun select(page: Int, loop: List<Pt>, answer: (List<Item>) -> Unit)`: on the worker, `Lasso.selects(items(page), loop)`, passed to `answer` (on the worker; the caller hops to the UI thread).
  - `fun items(page: Int, answer: (List<Item>) -> Unit)`, for the selection preview.
  - `fun rotate(pages: List<Int>)`: on the worker, reads each page's rotation and records one `RotatePages` turning each by +90.
  - `fun undo()`, `fun redo()`: record the inverse of the top of the undo stack (or redo the top of the redo stack) without clearing redo. At most `HISTORY_LIMIT = 200` undo steps.
  - New events: `data class PageChanged(val pages: Set<Int>, val rotated: Boolean)` after a change has reached the PDF (the screen re-renders those pages, and re-reads sizes when `rotated`), and `data class HistoryChanged(val canUndo: Boolean, val canRedo: Boolean)`. `Replayed(count)` now counts changes.
  - `ReplaceItems` coming in with `"o…"` ids in `after` gets fresh ids before journaling (Task 3's note).

**The ordering rule** (the one thing this task must get right): a change is journaled, appended to `unsaved`, and posted to the worker **inside one `synchronized(lock)` block**. Then the order in the journal, in `unsaved`, and on the worker is always the same, so the `applied` count still says exactly which changes a save contains. `erase` and `rotate` work out their change on the worker and then call `record` like anyone else; the change is applied when the worker reaches it, after anything posted before it.

Write the rule in a comment above `record`.
