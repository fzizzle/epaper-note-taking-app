# Android e-paper notes review

The highest-impact findings concern ownership of unsaved handwriting during file operations and recovery. The existing journal, PDF version checks, and device tests give the app useful recovery machinery. The gaps below occur where two mechanisms interact.

This is a static review of the supplied source, Gradle files, and tests. I did not run a build, the tests, or a tablet benchmark. Source references below are relative to `notes/app/src/main/java/com/fzizzle/epapernotes/` unless a different base is given. JVM test references use the corresponding package under `notes/app/src/test/java/`.

## Confirmed code problems, ranked by impact

1. **High — Moving a PDF can strand its unsaved handwriting while reporting success.** `library/FileOps.kt:165–174` moves the document first, migrates its journals and remembered page, then returns Done. A failed journal rename only writes to the log at lines 206–213. Process death between the document move and journal migration produces the same split. The PDF opens at its new path while its latest edits remain keyed to its old one. A folder move can stop after migrating only some children. Persist a recoverable old-to-new path mapping before moving the document, replay unfinished migrations on startup, and surface a partial result until all live journals are reachable. Extend `library/FileOpsTest.kt:96–139` with interruption after the PDF move and failure on the second journal in a folder.

2. **High — A destination that appears during rename can be overwritten.** `library/FileOps.kt:44,161–165,183–190` uses a destination check followed by a separate replacing-capable rename. The second check handles arrivals during the session wait, but another writer can create the file between that check and the move. The same gap exists when restoring a stranded rename at lines 340–346. Require a move primitive with an enforced no-replace guarantee on the supported filesystem, or decline the operation where that guarantee cannot be provided. Add a deterministic test that creates the competing file inside the injected move operation. The arrival-during-wait test at `library/FileOpsTest.kt:432` exercises an earlier point.

3. **High — Library containment checks miss symbolic links in ancestor directories.** `library/FileOps.kt:103–108,267–280,300–314` checks a lexically normalized path against the root and inspects the final component for a link. Given a linked directory inside the root and an ordinary file beneath it, the child passes both checks and deletion resolves through the link. This is a defect in the operation boundary. Exposure through the UI depends on the filesystem and how the path reaches the operation. Reject linked ancestor components and revalidate destructive operations against the actual library root. Extend the direct-link test at `library/FileOpsTest.kt:278` with a nested child and verify that the outside file survives.

4. **High, conditional on a damaged journal — Recovery can discard a valid edit after a completed save.** `doc/ChangeJournal.kt:268–284` omits undecodable changes, while `doc/DocumentSession.kt:182–185` drops the saved count from the resulting compacted list. For example, if a saved prefix contained two records, one becomes unreadable, and a third valid stroke follows the save marker, recovery drops both surviving records. The third stroke is then absent from both the PDF and the rewritten journal. Track original change positions or persist a stable save boundary, and preserve the journal for recovery when the prefix cannot be reconciled. Combine the missing-picture and marker scenarios already tested separately at `doc/ChangeJournalTest.kt:323,339`. This concerns a damaged complete record, beyond ordinary truncated-tail handling.

5. **Medium — Pen-up waits for durable I/O before the app can hand the stroke to the page overlay.** `ui/WritingActivity.kt:976–995` converts the samples and calls addStroke before posting the visual handover. `doc/DocumentSession.kt:401–417,474–492` waits for journal readiness and appends under the shared lock. `doc/ChangeJournal.kt:308–315` opens, writes and syncs the file. This is confirmed blocking work on the caller's path. Its duration and visibility on Onyx fast ink require measurement. Instrument callback entry, sync completion, overlay handover, and the next stroke start. If tail latency is significant, separate immediate visual feedback from durable acknowledgement using an ordered writer. Preserve save, undo, close, and crash-replay ordering. The device timings in `notes/app/src/androidTest/java/com/fzizzle/epapernotes/check/SpeedCheck.kt:95,158` provide useful full-page workloads.

6. **Medium — The probe adds synchronous file I/O to the input it measures.** Both the surface callback and Onyx reporting path call the logger directly (`probe/app/src/main/java/com/fzizzle/epapernotes/probe/MainActivity.kt:38–44` and sibling `OnyxInput.kt:49`). Sibling `ProbeLog.kt:26–32` formats the time and appends to disk while holding a monitor shared by producers. This can distort event spacing and ordering observed across callbacks. Capture monotonic arrival times at callback entry, enqueue to a bounded writer, and report dropped records and flush state. Keep the synchronous mode available for kill-recovery investigations. Compare the two modes on the same stroke sequence before drawing latency conclusions.

## Ideas to validate separately

- **Rendering memory and redraw cost.** `ui/PageView.kt:153–160,180–184` budgets 200 MiB for cached pages and separately owns patch bitmaps. Lines 839–875 traverse overlay points on redraw. Neither number establishes a memory fault or a slow frame. On a target tablet, measure peak process memory, cache misses, and frame times during rapid page turns and zoom on an ink-heavy PDF. Tune the cache or cache transformed geometry only if the measurements identify a bottleneck.
- **Maintainability.** The path migration in finding 1 deserves one explicit operation with persisted progress and a typed outcome. This gives the UI enough information to distinguish a completed move from one with handwriting still awaiting recovery. For rendering, preserve the existing independently testable bitmap cache and handover logic. If changing render scheduling, extract the request/arrival state transitions currently spread across `ui/PageView.kt:447–468,584–659,748–768` so stale results, navigation, and release can be exercised as event sequences.
- **Delete confirmation can age while displayed.** `ui/LibraryChanges.kt:120–138` counts on a worker and subsequently deletes by path after confirmation. Files added while the dialog is open will be included by the fresh recursive traversal at `library/FileOps.kt:267–272`. For libraries modified by another app or mounted elsewhere, compare a fresh inventory with the confirmed one and ask again on material changes. Test an insertion while the dialog is open.
- **Release identity.** `notes/app/build.gradle.kts:22–29` intentionally signs release builds with the local debug key for in-place tablet updates. If builds must be installed from more than one machine, define a stable signing identity and test an upgrade with an unsaved journal before changing distribution. A signing change affects existing installations.

The first regression tests I would add exercise interrupted journal migration, destination creation at the actual rename, a linked parent, and damaged-prefix replay. All four have observable pass criteria on disk. Pen and rendering changes warrant device measurements because source inspection establishes where work happens but cannot establish panel latency.
