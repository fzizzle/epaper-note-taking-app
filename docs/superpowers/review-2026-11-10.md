# Project review, 2026-11-10

Reviewed: the `library` branch at commit `ddd23eb` (all of `notes/app/src/main`, about 5,000 lines), against the [design](specs/2026-11-07-epaper-pdf-notes-design.md).

Not reviewed: the uncommitted SD-card work in the main checkout (`Volume.kt`, `StorageVolumes.kt` and the edits around them), because another session is still writing it.

How it was done: the code was read in three parts (PDF and saving, writing screen, library). Nothing was built or run on the tablet. Each finding says how sure it is:

- **Checked** — I traced the code path myself after the first read.
- **Read** — found by reading, with a clear path to the failure, not traced a second time.
- **Likely** — depends on timing or on how the tablet behaves; needs a test on the device.

Nothing in the code was changed. Every fix below is a proposal.

## 1. Bugs worth fixing first

### 1.1 Strokes get a small hole at each end and at sharp corners (Checked)

`ink/StrokeOutline.kt:59-71`. The body of a stroke is drawn clockwise and the round caps counter-clockwise. Since they are all filled in one go, the two directions cancel where a cap overlaps the body, and that patch is left unpainted.

- A highlighter stroke (6 pt radius) gets a half-circle gap just inside each end, and a round gap at every sharp turn. A pen stroke gets a nick of 0.3–1 pt, easy to miss.
- The tests miss it: one uses a stroke so short that both caps overlap each other, the others sample the middle.
- Fix: draw the caps in the same direction as the body (reverse the four curves in `circle`). Add a test that samples just inside the end of a long highlighter stroke.
- Strokes already saved keep the faulty drawing. The "redraw old ink" check (`isFaulty`) would need a second rule to find them.

### 1.2 After moving a zoomed page with one finger, writing lands in the wrong place (Checked)

`ui/PageView.kt:290-299`. A pinch tells the writing screen the page has moved; a one-finger move does not (`onScroll` never calls `onViewportChanged`). The pen keeps the mapping from before the move, so the next strokes are saved shifted by the distance moved. Lasso and eraser traces use the same stale mapping. A pinch or page turn afterwards hides it.

- Fix: one line, call `onViewportChanged()` in `onScroll` (or once when the fingers lift).

### 1.3 A failed journal write crashes the app on the pen's thread (Read)

`doc/DocumentSession.kt:273-274`. If the tablet's private storage is full, `journal.append` throws. Nothing catches it, so the app crashes with the stroke just written in neither the journal nor memory, and crashes again on every next stroke.

- Fix: catch it, keep the change in memory, save to the PDF at once, and tell the owner that writing can't be kept safe.

### 1.4 Errors on the document's worker thread vanish (Checked)

`doc/Scheduler.kt:31-37`. Java's scheduled executor stores a task's exception and never reports it.

- If reading or rewriting the journal fails during opening, no "couldn't open" message is sent and the screen waits forever.
- `save()` catches `Exception` but not out-of-memory. A save that runs out of memory fails with no message and no retry. That is the silent failed save the design names as the worst failure.
- Fix: wrap every posted task so anything thrown is logged; make opening report failure; catch `Throwable` in `save()`.

### 1.5 A stroke begun during the 150 ms screen update can be dropped (Likely)

`ui/WritingActivity.kt:793-807`. After an erase, undo or zoom the app pauses fast-ink for 150 ms to put the new picture on screen. With the pen or highlighter chosen, nothing listens to the pen in that gap, and fast-ink is switched back on mid-stroke. Erase-then-keep-writing is the likely way to hit it.

- Fix: let the screen trace the pen during every pause. The code for that already exists for the tools.
- This ties in with the open to-do "screen-recording test of writing".

### 1.6 The "damaged file" question can crash, and doesn't pause the pen (Read)

`ui/WritingActivity.kt:904`, `923-931`. If the owner leaves a damaged file before it finishes opening, the question is shown on a closed screen, which crashes. Unlike the other two dialogs it also doesn't pause fast-ink, so the box may not appear properly and pen taps on it would mark the page below.

- Fix: don't show it once the screen is closing, and give it the same pause as the other dialogs.

## 3. Build and setup

- **The adb test hooks work in every build (Checked).** `ui/LibraryActivity.kt:114-124`. Any app on the tablet can start the library with a `root` extra and silently change the library folder, or open any file with `path`. No file is harmed. Fix: accept them only in a debug build.
- **There is no release build (Read).** `notes/app/build.gradle.kts`. The tablet runs the debug build, which Android runs with extra checks on every call into MuPDF and Onyx. A release build is probably faster for rendering and saving. Not measured; the speed check could measure it. If added, keep code shrinking off, or MuPDF and Onyx break.
- **`minSdk` is 29 but the library uses Android 11 calls (Read).** Harmless on this tablet. Set it to 30.

## 4. Speed and efficiency

Ordered by how much I expect each to matter in use. None is measured.

### 4.1 Every autosave reads the whole PDF twice and rewrites it once

`doc/DocumentSession.kt:457-470`. Each save hashes the file, rewrites all of it, then hashes it again, on the one thread that also draws pages. On a big lecture file, a page turn or an erase made just after a pause in writing waits behind it. Opening also hashes the file before showing the first page.

- Cheap part: compare size and date first, and hash only when they match; take the after-save fingerprint from the temporary file before it is swapped in (this also fixes 2.1).
- Larger part, needs approval and a tablet test: save only the changes during a session, and do the full tidy rewrite when the document is left.

### 4.2 Each finished stroke redraws every stroke written on the page so far

`ui/PageView.kt:156-159`, `259-282`. After 500 strokes on a page, each pen lift costs tens of thousands of drawing calls on the main thread, for a frame the panel doesn't even show while fast-ink is on.

- Fix: don't redraw on a new stroke while fast-ink is on. The code already redraws before anything is shown.

### 4.3 Each added stroke costs more the fuller the page is

`pdf/PdfFile.kt:139-153`, `226-234`. Adding one stroke loads the page, walks every existing annotation to check for duplicates, then updates them all. On a dense page that is thousands of calls per pen lift, and replaying a journal grows with the square of the stroke count.

- Fix: remember the ids on each page instead of rereading them.

### 4.4 Every erase, move, paste or undo re-renders the whole page into a new picture

`ui/PageView.kt:166-170`, `ui/PageBitmaps.kt:26-34`. Old pictures are left for the garbage collector rather than freed at once, and leaving a page with new ink throws its picture away only for it to be rebuilt straight away as a neighbour.

- Fix: free pictures when they leave the cache. Later, re-render only the patch that changed (`renderRegion` already exists).

### 4.5 Dragging a selection redraws the whole page on every pen move

`ui/SelectionLayer.kt:129-141`, `243-282`. The preview shapes are rebuilt from scratch each time, and a traced lasso line is rebuilt from its first point.

- Fix: build the shapes once when the selection is made and just shift them; extend the lasso line instead of rebuilding it.

### 4.6 Smaller ones

- **Snips in the journal.** Each move, delete or undo of a snip writes its whole picture into the journal again, twice for a move, on the main thread (`doc/ChangeCodec.kt:20-25`). Store the picture once and refer to it.
- **Moved snips are decoded and encoded again** (`pdf/ItemAnnotations.kt:150-179`). Remember the picture when adding it.
- **Laying out a document loads every page twice**, and again in full after rotating even one page (`ui/WritingActivity.kt:344-358`).
- **A neighbour page arriving redraws the screen** though nothing visible changed (`ui/PageView.kt:203`).
- **Pinching calls the Onyx SDK several times per movement** for settings that only matter when the pinch ends (`ui/WritingActivity.kt:267-273`).
- **A pinch ends in two panel updates:** the clean refresh, then another when the sharper picture arrives.
- **The library redraws its "Continue" row on every listing,** changed or not, and a changed file's tile is redrawn twice (`ui/LibraryActivity.kt:280-284`, `ui/LibraryTiles.kt:127`).
- **Refresh rebuilds every thumbnail in the folder,** not just those on screen. This looks deliberate (commit `0c40336`); in a folder of several hundred PDFs it means minutes of work.

## 6. Making PDFs easier to read, without touching the file

Today a page goes from MuPDF to the screen with nothing done to it: no contrast, colour or sharpness step, and no e-ink update mode asked for except the full flash after a zoom. So there is room. Everything below changes only the picture drawn on screen. The PDF, the saved ink and snips are untouched, and other viewers see no difference.

These are feature changes, so each needs the owner's approval before it is built.

### 6.1 Sharp text when zoomed in — recommended first

Zoomed in, the page is drawn at 1.5× its fitted size and then stretched, up to 4×. Past 1.5× the text is blurred by the stretching. This is the biggest loss of readability in the app today, and it is exactly when the owner has zoomed in to read something small.

- Change: once the fingers lift, draw just the part of the page on screen at its true size. `renderRegion` already does this for snips, and a screen-sized picture costs less memory than today's 1.5× whole page.
- Cost: one extra render after each zoom or move, which is already followed by a refresh.

### 6.2 A contrast setting

Kaleido colour panels show greys and colours paler than the file intends: thin grey text and pastel slide backgrounds are the usual complaints. A contrast step applied to the page picture as it is made (on the worker thread, once per render, not on every redraw) darkens text and thin lines.

- Change: one setting with three steps, "Off / Stronger / Strongest", in the page menu or library settings, remembered in the app's own settings.
- Snips must be cut from the untouched page, so a pasted picture doesn't get the contrast applied twice. They already are, because snips are rendered separately.
- Cost: a pass over the picture's pixels after each render, a few tens of milliseconds. Worth trying on one slide deck before deciding the steps.

### 6.3 Trim white margins

Slides and papers often carry wide empty margins. Fitting the printed area rather than the whole page makes everything larger at normal size, with no zooming.

- Change: a "Trim margins" switch. The app finds the empty border from a small render of the page and fits the rest to the screen.
- Cost: a little work per page, done once. More code than 6.1 or 6.2, because the pen's mapping must follow the trim.

### 6.4 Cleaner page turns

A page turn is put on the panel with the default update, which can leave a faint ghost of the last page behind the text. Asking Onyx for a cleaner update on a page turn (not the full flash) removes it. This overlaps with the open to-do "gentler refresh after zooming" and should be tried together with it on the tablet.

### 6.5 Something to try today, with no code

Boox lets the owner tune any app: long-press the app's icon → Optimize → Display. "Dark colour enhancement", "text bolding" and "background bleaching" there act on this app's pages too. If one of them is enough, 6.2 isn't needed. If it interferes with fast-ink or the highlighter's colour, that is useful to know before building 6.2.

### Suggested order

6.5 (a minute on the tablet), then 6.1, then 6.2 if still wanted, then 6.4 with the refresh to-do. 6.3 last.

## 7. Checked and found sound

- **Saving:** temporary file, flush, atomic swap, folder flush; the temporary file is removed on any failure; nothing is written to a repaired file before the owner decides.
- **Journal:** a torn last line is ignored; the rewrite is atomic; journal, memory and worker stay in the same order; changes made during a save are kept.
- **Stroke and snip data:** every kind round-trips, in any tablet language; old-format strokes still read.
- **Geometry:** the transform maths, rotation in all four turns, snip placement across pages of different rotation.
- **MuPDF:** every page, picture and device is released on every path; only one thread ever touches a document.
- **Tools:** eraser and lasso hit tests, pen-button mapping, selection move and resize maths, undo during a drag.
- **Library file changes:** a folder can't be moved into itself; name clashes are caught whatever the letter case; nothing outside the library folder can be touched; links are never followed on delete; journals and remembered pages follow a rename or move.
- **Thumbnails:** a file still being copied never leaves a stale picture; recycled tiles never show the wrong file; no file reading on the main thread.
- **Permissions:** the only one is All files access, and the writing screen can't be started by other apps.
