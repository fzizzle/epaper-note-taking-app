## Detailed Findings — Part I: Confirmed Problems

### 1. Correctness Bugs and Risky Code

#### 1.1 `WritingActivity.onPause()` queues `storeContinuePicture()` before `session.saveNow()` and races with conflict-copy creation (`SavedToCopy`)
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/WritingActivity.kt:1963-1991, 2095-2116`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/LibraryActivity.kt:289-302, 511-515`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/ContinuePicture.kt:19-48`
- **Problem:**
  1. In `WritingActivity.onPause()` (lines 1963–1966):
     ```kotlin
     pages.viewport?.let { lastPages.set(path, it.page, pageCount) }
     storeContinuePicture()
     // Going to the background or leaving: save now, not in a few seconds (spec §7.2).
     session.saveNow()
     ```
     `storeContinuePicture()` posts a task to the document's single worker thread (`session.runOnDocument`) that renders the current page at `CONTINUE_WIDTH_PX = 300`, compresses it to PNG, and writes it to disk. `session.saveNow()` posts `save()` to the **same single worker thread behind `storeContinuePicture()`**.
     - First, this violates Spec §4 (Anti-goal 1: saving is the most protected part of the design): when the user leaves the app or backgrounds it, the critical PDF save waits behind a cosmetic cache thumbnail render (and unlike `ThumbnailLoader.render` at `ThumbnailLoader.kt:402`, `storeContinuePicture()` does not use `thumbWidthPx(size.width, size.height)`, so on a very tall page it renders an uncapped height bitmap before saving!).
  2. Second, if the PDF was modified on disk while open (e.g. by Syncthing) and the user wrote strokes within the last 10 seconds before tapping `←` to leave:
     - `onPause()` runs on the UI thread while `path` is still `original.pdf`. It records `lastPages.set(originalPath, ...)` and queues `storeContinuePicture()` with `val pdfFile = File(path)` (`original.pdf`).
     - Then `save()` runs on the worker thread, detects the conflict (`fileUnchanged() == false`), creates `original (my edits YYYY-MM-DD).pdf` via `continueInCopy()`, and posts `runOnUiThread { show(SessionEvent.SavedToCopy(copy, ...)) }`.
     - Even when `show(SessionEvent.SavedToCopy)` runs on the UI thread (`WritingActivity.kt:2095-2116`), it updates `lastPages` and `LibraryPrefs(this).lastOpened = event.copy`, **but it never updates `ContinuePicture` (`prefs.continuePictureOf`)**, which `storeContinuePicture()` already bound to `original.pdf`! Thus `continuePicture.load(resume.file)` returns `null` (`ContinuePicture.kt:40`).
     - Meanwhile, `LibraryActivity.onResume()` (`LibraryActivity.kt:299-302`) and `LibraryActivity.list()` (`LibraryActivity.kt:511`) capture `val last = prefs.lastOpened`, `afterSaveOf`, and `cameBackFrom` on the **main thread before** `disk.execute` calls `DocumentSession.awaitClosed(it, LEFT_SAVE_WAIT_MS)`!
     - As a result, when `awaitClosed` finishes, `LibraryActivity` builds the `Continue` row and `cameBackFrom` highlight using the stale `original.pdf` captured before `SavedToCopy` ran, rather than the `(my edits ...)` copy where the user's writing actually went.
- **Fix:**
  - In `WritingActivity.onPause()`, call `session.saveNow()` **before** `storeContinuePicture()`.
  - Inside `storeContinuePicture()`, read `session.file` on the worker thread (after `save()` has completed and potentially switched `session.file` to the conflict copy) and cap the width with `thumbWidthPx(size.width, size.height)`.
  - In `WritingActivity.show(SessionEvent.SavedToCopy)`, also call `ContinuePicture(cacheDir, LibraryPrefs(this)).moved(oldFile, event.copy)`.
  - In `LibraryActivity.list()`, read `prefs.lastOpened` (and resolve `cameBackFrom` if it switched to a copy) **after** `DocumentSession.awaitClosed(...)` completes (or re-read it on the main thread before `showListing`).

#### 1.2 Fast-ink remains enabled under system overlays (`onWindowFocusChanged(false)`)
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/WritingActivity.kt:1940-1944`
  - `docs/superpowers/findings-log.md:53-70`
- **Problem:**
  - `WritingActivity.onWindowFocusChanged` currently only logs `focus=$hasFocus fast-ink=${pen.drawsInk} dialog=$dialogOpen`.
  - As confirmed on the tablet in `findings-log.md:53-70`, pulling down the Android notification shade or opening the power menu causes the window to lose focus (`hasFocus = false`) with `dialogOpen = false`, without calling `onPause()`.
  - Because `pen.drawsInk` (`TouchHelper.setRawDrawingEnabled(true)`) stays on, Boox's EPDC raw-drawing driver continues intercepting stylus input across `penLimit()`. Tapping or dragging with the pen in the notification shade or system dialog writes raw ink onto the panel and delivers the points to `PenInput.callback`, recording unintended strokes or erases onto the document page underneath.
- **Fix:**
  - Track window focus in `WritingActivity` (e.g. `hasWindowFocus: Boolean`, included in `fastInkWanted()`). When `onWindowFocusChanged(false)` fires while `!dialogOpen`, pause fast-ink (`pausePenAndRedraw()` or once any stroke in progress lifts); when `onWindowFocusChanged(true)` fires, schedule `resumeFastInk` after `SHOW_PAUSE_MS`.

#### 1.3 Missing `pen.isWriting || screenPenDown` guards on strip and gesture actions in `WritingActivity`
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/WritingActivity.kt:1120, 1376, 1404, 1416, 1744`
- **Problem:**
  - In `onKeyDown` (line 1927) and `goToEnd` (line 1773), page turns are explicitly blocked while `!documentShown || pen.isWriting || screenPenDown || pageChangeUnderWay` because turning the page or opening a dialog mid-stroke either cuts the stroke in progress or lands it on the wrong page.
  - However, five other entry points in `WritingActivity.kt` omit some or all of these checks:
    1. `turn(forward: Boolean)` (line 1744, called by tapping `‹` or `›` in the strip): checks only `if (pageChangeUnderWay) return`. If a resting hand or finger taps `‹` or `›` while `pen.isWriting` or `screenPenDown` is true, `pages.turn(forward)` mutates the viewport to the new page mid-stroke while `showWithoutFastInk()` skips the panel refresh (`show skipped: pen is down`).
    2. `askForPage()` (line 1376, called by tapping the page number): checks only `if (pageChangeUnderWay) return`. Tapping it while `pen.isWriting` or `screenPenDown` or `dialogOpen` is true immediately increments `windowsOpen`, calls `pausePenAndRedraw()`, and cuts the stroke in progress.
    3. `undoOrRedo(undo: Boolean)` (line 1404): checks only `if (pageChangeUnderWay) return`, not `pen.isWriting || screenPenDown`.
    4. `openPageMenu()` (line 1416): checks `if (pen.isWriting) return` and `if (pageChangeUnderWay) return`, but omits `screenPenDown` and `dialogOpen`.
    5. `offerPaste(x, y)` (line 1120): checks `pen.isWriting`, `dialogOpen`, and `pageChangeUnderWay`, but omits `screenPenDown` and `fingerGesture`.
- **Fix:**
  - Guard `turn`, `askForPage`, `undoOrRedo`, `openPageMenu`, and `offerPaste` consistently against `pen.isWriting || screenPenDown || fingerGesture || pageChangeUnderWay` (and `dialogOpen` for dialog/popup launchers).

#### 1.4 Double full-file read on document open creates a TOCTOU window between `FileIdentity` and `PdfFile.open(inMemory = true)`
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/doc/DocumentSession.kt:155-159, 211-216`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/pdf/PdfFile.kt:602-615`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/WritingActivity.kt:457-461`
- **Problem:**
  - When `WritingActivity` opens a PDF (up to 64 MB):
    1. `DocumentSession.openOnWorker()` calls `identityOf(file)` (`DocumentSession.kt:156`), which streams the entire file from disk to compute its SHA-256 (`FileIdentity.of`).
    2. `openOnWorker()` reads/rewrites the journal (`DocumentSession.kt:167-205`).
    3. `openOnWorker()` calls `open(file)` (`DocumentSession.kt:212`), which calls `PdfFile.open(it, inMemory = true)` (`PdfFile.kt:614`), reading the entire file from disk a **second time** via `file.readBytes()`.
  - If an external process (Syncthing, USB copy) modifies or replaces `file` during the 20–80 ms window between step 1 and step 3, `known` (`identity`) holds the SHA-256 of the old file while `pages` in memory holds the new file's bytes (or vice versa). On the next save, `fileUnchanged()` compares the file on disk against `known`, falsely detects a conflict (or misses one), and writes a copy from mismatched bytes.
- **Fix:**
  - For files `<= PdfFile.IN_MEMORY_LIMIT_BYTES`, read the file's `ByteArray` once on open, compute `FileIdentity` directly from that `ByteArray` (plus `lastModified()`), and pass the same `ByteArray` into `Document.openDocument(bytes, "pdf")`.

#### 1.5 `ThumbnailCache.storeFacts` omits `<hash>.path`, causing `pruneMissing()` to delete all List-View `.facts` files daily
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/library/ThumbnailCache.kt:50-73, 102-121`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/ThumbnailLoader.kt:350-361`
- **Problem:**
  - When the library is in Tiles View, `ThumbnailCache.store(pdf, png)` writes `<hash>-<size>-<modified>.png`, writes `<hash>.path` containing the PDF's path, and sweeps older `<hash>-*` files (`ThumbnailCache.kt:50-61`).
  - When the library is in List View (`prefs.listView = true`), no PNG thumbnails are generated; instead, `ThumbnailLoader.loadFacts(pdf)` (`ThumbnailLoader.kt:350-361`) calls `cache.storeFacts(pdf, it)`.
  - `ThumbnailCache.storeFacts(pdf, facts)` (`ThumbnailCache.kt:69-72`) only writes `<hash>-<size>-<modified>.facts`: it **never writes `<hash>.path`** and **never sweeps older `<hash>-*.facts` files** for that PDF.
  - When `ThumbnailCache.pruneMissing()` runs once a day (`ThumbnailCache.kt:102-121`), it populates `live` exclusively from `<hash>.path` files (`if (!side.name.endsWith(".path")) continue`) and deletes every `.png` and `.facts` file whose hash is not in `live` (`line 117`).
  - Thus, for any PDF browsed only in List View, its `.facts` file has no matching `.path` file and is deleted by `pruneMissing()` every day, forcing MuPDF to reopen and scan up to 300 pages of every PDF again.
- **Fix:**
  - In `ThumbnailCache.storeFacts(pdf, facts)`, also write `File(dir, "$hash.path")` if absent and sweep stale `$hash-*.facts` files (whose name is not `factsFileFor(pdf).name`).

#### 1.6 `LibraryActivity.list()` does not pass opened-out small subfolders (`PdfEntry.group`) to `index?.reread(...)`
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/LibraryActivity.kt:520, 551, 829, 837-838`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/library/IndexCheck.kt:50-56, 107`
- **Problem:**
  - With `prefs.openOutSmallFolders = true` (the default), `FolderListing.list(shown, 3)` opens out subfolders holding 1–3 PDFs and lists their PDFs directly in `shown` with `pdfEntry.group = subfolder`.
  - `FolderWatch.watchChildren(watchedChildren())` watches those opened-out subfolders on screen (`LibraryActivity.kt:837-838`) and triggers `list()` when a file is added, renamed, or deleted inside one of them.
  - At the end of `list()` (`LibraryActivity.kt:551`), the library notifies the search index via `index?.reread(listOf(shown))`.
  - However, in `IndexCheck.visit` (`IndexCheck.kt:107`), a `reread` visit only descends into **newly created** subfolders (`val next = if (visit.reread) read.folders - held.toSet() else read.folders`) and intentionally skips subfolders already known to the index!
  - Consequently, when a file arrives in or is removed from an existing opened-out topic subfolder, `LibraryActivity` shows the change immediately on screen, but `index?.reread(listOf(shown))` never re-reads the opened-out subfolder. If the user then taps Search and types a query, `SearchPreviewView` (`index.preview`, which does not check the card) queries the stale index and misses the PDF that is already visible on the grid behind the search dialog.
- **Fix:**
  - In `LibraryActivity.list()` (line 551), pass the opened-out group folders along with `shown`:
    `index?.reread(listOf(shown) + entries.mapNotNull { (it as? PdfEntry)?.group }.distinct())`.

#### 1.7 `PageView.onTouchEvent` multi-touch pointer-type check and rescued-pinch `GestureDetector` state bug
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/PageView.kt:951-1027`
- **Problem:**
  1. In `PageView.onTouchEvent` (line 979):
     ```kotlin
     if (ignoringFingers && event.actionMasked == MotionEvent.ACTION_POINTER_DOWN && fingersAllowed()) {
         android.util.Log.i("Notes", "second finger: a pinch, not the palm")
         ignoringFingers = false
     ```
     `isPen(event)` (line 1024) and line 968 only check `event.getToolType(0)` (pointer index 0). If a palm touches the screen while the pen is hovering near it (`penNear == true`, so pointer 0 is `TOOL_TYPE_FINGER` and `ignoringFingers = true`), and then the stylus touches down while the palm is still in contact (`ACTION_POINTER_DOWN` with `actionIndex = 1`, `getToolType(1) == TOOL_TYPE_STYLUS`), line 979 does not check `event.getToolType(event.actionIndex) == MotionEvent.TOOL_TYPE_FINGER`. It treats the stylus touch-down as a "second finger", clears `ignoringFingers`, and feeds the palm + stylus into `ScaleGestureDetector` to pinch-zoom the page instead of routing the stylus to `penHandler` (when fast-ink is off for Lasso/Snip/Paste).
  2. When a genuine two-finger pinch is rescued at line 979 after `ACTION_DOWN` was ignored at line 988, `scroller` (`GestureDetector`) never saw the initial `ACTION_DOWN` event (so its internal `mStillDown` flag is `false`). If the user pinches to zoom in and then lifts one finger to pan with the remaining finger, `GestureDetector.onScroll` ignores the pan until all fingers lift and touch down again.
- **Fix:**
  - At line 979, verify `event.getToolType(event.actionIndex) == MotionEvent.TOOL_TYPE_FINGER`.
  - When rescuing a pinch on `ACTION_POINTER_DOWN`, synthesize or forward a down state to `scroller` (or feed `ACTION_DOWN` to `scroller` while suppressing `onSingleTapUp`/`onLongPress` when `ignoringFingers` is true) so one-finger panning works seamlessly after lifting one finger of a rescued pinch.

#### 1.8 `WorkerScheduler` delayed tasks survive `shutdown()`, and `close()` shows a misleading retry toast on save failure
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/doc/Scheduler.kt:33-38, 50-58, 74-76`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/doc/DocumentSession.kt:791-807, 880-888`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/WritingActivity.kt:2049-2056`
- **Problem:**
  1. In `WorkerScheduler`, `ScheduledThreadPoolExecutor` defaults to `executeExistingDelayedTasksAfterShutdownPolicy = true` (unlike `NameIndex.readerThread` at `NameIndex.kt:90`, which sets it to `false`). Any delayed task not explicitly cancelled before `shutdown()` keeps the worker thread and its captured `DocumentSession` alive for up to 30 seconds (`RETRY_DELAY_MS`).
  2. When `DocumentSession.close()` calls `save()` and that final save fails (`DocumentSession.kt:797, 880-888`), `save()` emits `SessionEvent.SaveFailed` and attempts `scheduler.postDelayed(AUTOSAVE, RETRY_DELAY_MS) { save() }`, after which `close()` immediately closes `pages` (`pages = null`) and shuts down the scheduler. `WritingActivity.show` (`WritingActivity.kt:2050`) then shows a toast: `"Couldn't save: … Your writing is kept safe and will be saved again"` (or `"saving is tried again every half minute"`), even though no background retry can happen after the document is closed (the unsaved changes wait in the journal until the user reopens the file).
- **Fix:**
  - Set `executeExistingDelayedTasksAfterShutdownPolicy = false` on `WorkerScheduler.executor` in `Scheduler.kt:33`.
  - Pass a `closing: Boolean = false` flag into `save()` from `close()` so a save failure during close does not schedule a dead retry and emits a message telling the owner that the writing is safe in the app and will be saved when the file is reopened.

#### 1.9 Float finiteness (`NaN` / `Infinity`) in `StrokeCodec`, `ItemCodec`, `Stroke`, and `StripButton`, plus negative capacity in `DottedPaper`
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ink/StrokeCodec.kt:105`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ink/ItemCodec.kt:58`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ink/Stroke.kt:21-25`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/StripButton.kt:109-111`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/pdf/DottedPaper.kt:24-36, 56-57`
- **Problem:**
  - Kotlin's `String.toFloatOrNull()` parses `"NaN"`, `"Infinity"`, and `"-Infinity"` as valid `Float` values (`Float.NaN`, `Float.POSITIVE_INFINITY`, `Float.NEGATIVE_INFINITY`). `StrokeCodec.slow` (`StrokeCodec.kt:105`) and `ItemCodec.decodeImage` (`ItemCodec.kt:58`) do not filter with `.takeIf(Float::isFinite)`, nor does `Stroke.init` (`Stroke.kt:21-25`) require finite coordinates/pressures/widthScale. If a `NaN` reaches `StrokeOutline.contentStream`, `String.format(Locale.ROOT, "%.1f", v)` writes literal `"NaN"` tokens into the PDF appearance stream.
  - In `StripButton.onSizeChanged` (`StripButton.kt:109-111`), if `w == 0` or `h == 0`, `s = 0f`, making `len = hypot(0f, 0f) = 0f` and dividing `0f / 0f = Float.NaN` when building `penMark`.
  - In `DottedPaper.count(lengthPt)` (`DottedPaper.kt:57`), `floor((lengthPt - SPACING_PT) / SPACING_PT).toInt() + 1` is not clamped with `.coerceAtLeast(0)`, which can produce a negative count and throw `IllegalArgumentException` in `ArrayList(columns * rows)` if given a negative dimension.
- **Fix:**
  - Add `.takeIf { it.isFinite() }` to `StrokeCodec.slow` and `ItemCodec.decodeImage`, validate finiteness in `Stroke.init` and `Box`, guard `if (s <= 0f) return` in `StripButton.onSizeChanged`, and add `.coerceAtLeast(0)` to `DottedPaper.count`.

### 2. Performance (Especially E-Paper Rendering & Pen Latency)

#### 2.1 Redundant `journal.rewrite` + `fsync` on every document open when the journal is empty
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/doc/DocumentSession.kt:175-190`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/doc/ChangeJournal.kt:109-129`
  - `docs/superpowers/efficiency-results.md:22`
- **Problem:**
  - In `DocumentSession.openOnWorker()`, whenever a PDF is opened—even when there are **zero** unsaved changes (`old == null || old.changes.isEmpty()` or `old.base.sameContentAs(identity)` with `old.changes.isEmpty()`)—the worker thread synchronously executes `journal.rewrite(identity, emptyList())` before opening the PDF in MuPDF and before rendering page 1.
  - `journal.rewrite` creates a `.journal.new` file, writes the header, calls `out.fd.sync()`, atomically renames it over `.journal`, and calls `SafeSave.syncFolder(file)`.
  - On the tablet (`efficiency-results.md:22`), this adds ~19 ms to the critical path before page 1 is even opened (and more when flash storage is busy), and leaves an empty `.journal` file in `filesDir/journals/` forever for every PDF ever viewed.
- **Fix:**
  - When `old != null && old.base.sameContentAs(identity) && old.changes.isEmpty() && old.pendingSave == null && !old.renumbering`, skip `journal.rewrite` entirely on open (the `pnj2` header on disk already matches `identity`).
  - Even better: when `old == null`, defer creating the `.journal` header file on disk until either the first change is recorded or after page 1 has been rendered and delivered to `PageView`.Combined with reading the file once on open (§1.4), this cuts ~76 ms (>50%) off the 133 ms document open time on a 14 MB PDF.

#### 2.2 `PdfFile.apply(RemoveItems)` and `removeOwnItems()` call `p.update()`, triggering an `O(N)` MuPDF annotation walk on every erase
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/pdf/PdfFile.kt:396-404, 437`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/pdf/ItemAnnotations.kt:104-117`
- **Problem:**
  - `ItemAnnotations.addInk` (`ItemAnnotations.kt:108-117`) notes that `p.update()` in MuPDF 1.28.5 walks every annotation on every loaded page twice (`pdf_update_annot`). For that reason, `PdfFile.add` returns `LEAVE_PAGE_ALONE` (`false`) for stroke additions, and `ReplaceItems` (`PdfFile.kt:400-404`, which calls `remove()` followed by `add()`) also returns `LEAVE_PAGE_ALONE` for stroke moves/resizes.
  - However, `RemoveItems` (`PdfFile.kt:396-399`) and `removeOwnItems()` (`PdfFile.kt:437`) still return `UPDATE_PAGE` (`true`), causing `onPage` to call `p.update()` after `p.deleteAnnotation(it)`. Because `p.deleteAnnotation(it)` already removes the annotation from the page's `/Annots` array (as proven by `ReplaceItems` in `PdfFileStrokesTest.kt:199-205`), calling `p.update()` on `RemoveItems` does unnecessary `O(N)` work on every erase on a full page.
- **Fix:**
  - Return `LEAVE_PAGE_ALONE` from `RemoveItems` and `removeOwnItems()`.

#### 2.3 `PdfFile.drawSolid` computes horizontal pixel bounds across the entire page instead of per-band
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/pdf/PdfFile.kt:187-207`
- **Problem:**
  - `drawSolid` computes `x0 = maxOf(bounds.minOf { it.x0 }, box.x0)` and `x1 = minOf(bounds.maxOf { it.x1 }, box.x1)` across **all** solid strokes on the page, and uses `w = x1 - x0` for every 256-row band (`drawSolidBand`).
  - If a page has even one short mark near the left margin and one near the right margin, every band that contains any ink allocates a `Pixmap`, copies `bmp.getPixels`, iterates in Kotlin, and calls `bmp.setPixels` across the full width of the page (`w ≈ 1700–2790 px`), even if `inBand` only contains a 40 px-wide margin tick.
- **Fix:**
  - Inside the `while (y0 < bottom)` loop (`PdfFile.kt:200-206`), compute `bandX0` and `bandX1` from the bounds of `inBand` only, and pass `bandX0` and `bandW = bandX1 - bandX0` to `drawSolidBand` (reusing `px` sized to the maximum band width).

#### 2.4 Search double-sorts up to 5,000 hits, allocates heavily inside comparators, and truncates in SQL ASCII order before natural-order sorting
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/NameIndexDb.kt:95-105`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/NameIndex.kt:288-298, 317`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/library/NameMatch.kt:42-61`
  - `notes/app/src/main/java/com/fzizzle/epapernotes/library/NaturalOrder.kt:10-31`
  - `notes/app/src/androidTest/java/com/fzizzle/epapernotes/ui/NameIndexDbTest.kt:157`
  - `notes/app/src/androidTest/java/com/fzizzle/epapernotes/check/SearchCheck.kt:74`
- **Problem:**
  1. **Double sorting:** `NameIndexDb.search(words, cap)` ends with `return Matches(total, NameMatch.arrange(hits, cap))` (`NameIndexDb.kt:104`). Its caller `NameIndex.found` (`NameIndex.kt:290-291`) calls `val m = store.search(NameMatch.words(query), SEARCH_CAP)` (`cap = 5000`) and then immediately calls `NameMatch.arrange(m.hits, NameMatch.SEARCH_LIMIT)` a **second time**, sorting all 5,000 already-sorted `Hit`s again before taking 200.
  2. **Per-comparison allocations:** Sorting 5,000 hits performs ~61,000 comparator calls (122,000 with the double sort). On **every single comparison**:
     - `NameMatch.compareFolders` (`NameMatch.kt:52-61`) calls `a.split('/').filter { it.isNotEmpty() }` and `b.split('/').filter { it.isNotEmpty() }`, allocating new lists and strings.
     - `NaturalOrder.compare` (`NaturalOrder.kt:18`) calls `BigInteger(a.substring(i, endA)).compareTo(BigInteger(b.substring(j, endB)))`, allocating substrings and `BigInteger` objects even for 1–2 digit numbers like `"Week 2"`.
  3. **Benchmark mismatch:** `NameIndexDbTest.twentyThousandNamesAnswerInUnder100Ms` (`NameIndexDbTest.kt:157`) and `SearchCheck.kt:74` call `db.search(..., 200)` instead of `NameIndex.SEARCH_CAP` (`5000`), testing only 1/25th of the rows and 1/2 of the sorts that `NameIndex.found` actually executes.
  4. **ASCII truncation before natural order:** When a query matches more than `cap` rows, SQLite's `ORDER BY f.path, p.file_name LIMIT $cap` (`NameIndexDb.kt:101`) truncates using binary ASCII order before Kotlin's natural-order sort runs, so `"Course 10"`..`"Course 99"` or uppercase paths can crowd out `"Course 2"` or lowercase paths.
- **Fix:**
  - Remove the redundant `NameMatch.arrange` call (either sort once in `IndexStore.search` and pass `limit = 200` alongside `fetchCap = 5000`, or sort only in `NameIndex.found`).
  - In `NaturalOrder.compare`, compare digit runs without allocating `substring` or `BigInteger` (skip leading zeros; if run lengths differ, the longer run is greater; if equal, compare characters in place; ties fall back to run length / string).
  - In `NameMatch.compareFolders`, walk `/` segments by index without `split('/').filter(...)`.
  - Update `NameIndexDbTest` and `SearchCheck` to benchmark with `SEARCH_CAP = 5000` (matching `NameIndex.found`).

#### 3.2 `NameIndexDb.put` deletes and re-inserts all PDF rows for a folder, breaking row-ID stability required by Spec §7.1 / §9
- **Locations:**
  - `notes/app/src/main/java/com/fzizzle/epapernotes/ui/NameIndexDb.kt:55-67`
  - `docs/superpowers/specs/2026-11-17-library-search-design.md:69, 128, 156`
- **Problem:**
  - `NameIndexDb.putRows` updates the `folders` row in place so it keeps its `id`, but then executes `db.delete("pdfs", "folder = ?", arrayOf(id.toString()))` and re-inserts every PDF in that folder with a new auto-increment `id`.
  - As noted in `2026-11-17-library-search-design.md:128, 156`, any future full-text search index (`§9`) keyed by `pdfs.id` will break unless `putRows` upserts PDF rows in place (`UNIQUE(folder, file_name)`) and deletes only vanished file names.
- **Recommendation:**
  - Add `UNIQUE(folder, file_name)` to `pdfs` (bumping `LAYOUT = 2`), update or keep existing `(folder, file_name)` rows in `putRows`, and delete only `file_name`s no longer present in `read.pdfs`.

## Detailed Findings — Part II: Speculative Ideas & Hardware-Dependent Explorations

These ideas are either dependent on Boox Note Air 6 C firmware/SDK behavior (requiring tablet experiments) or architectural enhancements beyond current confirmed bugs.

### S1. Mitigating the E-Ink Flash After Each Erase (`TODO.md:70`, `README.md:11`)
- **Context:**
  - When an erase removes a stroke (`WritingActivity.kt:1036-1049, 1792-1830`), the app currently drops the entire page bitmap (`PageView.pageChanged`, `PageView.kt:524-534`), re-renders the entire page in MuPDF, and calls `showWithoutFastInk()`, which calls `TouchHelper.setRawDrawingEnabled(false)` -> `EpdController.invalidate(pages, UpdateMode.REGAL)` -> 150 ms delay -> `TouchHelper.setRawDrawingEnabled(true)`.
  - As logged in `findings-log.md:124-136`, toggling `setRawDrawingEnabled(false)` triggers `SurfaceFlinger: Post enabled!` and `HWEpdcManager: ### EUS`, which causes a full-panel flash during the 165 ms pause.
- **Tablet Experiments Worth Trying:**
  1. **Dirty-rect region render + `showAlone` (`leaveScribbleMode` / `enterScribbleMode`) instead of `setRawDrawingEnabled(false)`:**
     - Compare `PenInput.showAlone` (`PenInput.kt:136-141`, used for the top strip) with `PenInput.pause()` + `resume()`. When `EraseSettle` fires after a hover-erase (`onHoverEraseTrail`, where Onyx never drew a grey trail into its scribble buffer!), Onyx's scribble buffer does not need to be cleared—only the erased stroke's bounding box in `PageView` needs to be redrawn and posted to the panel.
     - Furthermore, instead of re-rendering the entire page bitmap on every erase, `DocumentSession.erase` can return the bounding `Box` of the removed items (`hits`), allowing `PdfFile.renderRegion` to re-render only the dirty rectangle and blit it into the cached page `Bitmap`, followed by `pages.invalidate(dirtyRect)` and a regional `EpdController.invalidate`.
  2. **`TouchHelper.setRawDrawingRenderEnabled(false)` vs `setRawDrawingEnabled(false)`:**
     - In the Onyx Pen SDK (`com.onyx.android.sdk.pen.TouchHelper`), test whether toggling rendering or using `EpdController.setViewDefaultUpdateMode(pages, UpdateMode.REGAL)` with `leaveScribbleMode`/`enterScribbleMode` avoids the `HWEpdcManager ### EUS` flash that `setRawDrawingEnabled(false)` triggers.

### S2. Visual Feedback During Hover-Erase (`TODO.md:64`, `ui/HoverErase.kt`)
- **Context:**
  - When button 2 is pressed while the pen is already hovering close to the glass, the EMR digitizer reports hover events with pressure > 0.02 (`HoverErase.kt:20-26`) rather than `ACTION_DOWN`, so Onyx does not draw a live eraser trail.
- **Idea to Test on Tablet:**

(Note: while fast-ink is on, SurfaceFlinger posting is suppressed by Onyx, so any visual hover indicator would either need hardware cursor support or remain off to avoid flashing.)

### S3. Incremental / Partial Page Re-rendering on Move, Paste, and Erase (`ui/PageView.kt:524-534`)
- **Context:**
  - Currently, any non-stroke edit (`Erase`, `Move`, `Resize`, `Paste`, `Duplicate`, `Undo`, `Redo`) invalidates the full-page bitmap and (when zoomed in) the sharp patch, re-rendering both from scratch in MuPDF (~50–130 ms on a dense page).
- **Idea:**
  - Since `PdfFile.renderRegion(page, displayBox, pxPerPt, smoothInk = false)` already renders arbitrary sub-rectangles with solid ink matching the full-page render (`PdfFileStrokesTest.kt:139-155`), `PageChanged` could carry the dirty `Box` in PDF space (union of `before` and `after` item boxes) and update only that sub-rectangle of the cached `Bitmap` in place.
